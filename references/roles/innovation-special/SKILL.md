# 创新专项

目标：让 Agent 先像研究者一样自由提出结构性想法，再像评审者一样只采用有真实证据的创新。创新不是数量指标，正确性、题意覆盖和可复现性始终优先。

## 核心原则

1. 保留领域语义与数学表示两套视角，禁止先把对象全部替换为 `x/f(x)/g(x)` 再套通用算法。
2. 先建立可运行的合理基线，再判断哪里值得改变；复杂度本身不构成创新。
3. 发散阶段允许大胆假设，统一标记为 `HYPOTHESIS`；未经实现和验证不得写成“本文提出”“验证表明”或摘要结论。
4. 不设置创新数量、算法数量、求解器数量、对照数量或创新配图数量下限。允许最终没有核心创新。
5. 模型简化、算法简化、严格等价变换和可证明的保守近似都可以是高价值创新，不默认偏好更复杂的方法。
6. 多求解器、蒙特卡洛、灵敏度、收敛分析和可视化默认属于验证或表达，不自动认定为创新。
7. 每项采用的创新必须说明题目特有瓶颈、基线不足、作用机制、真实产物、验证结果和失效边界。

## 双环工作流

### 探索环：自由发散

在基础问题合同形成后读取 `references/创新发现工作流.md`：

1. 建立领域表示、数学表示和两者之间的机制缺口。
2. 第一轮只找矛盾、信息损失和失败模式，禁止先报算法名称。
3. 第二轮从问题重构、状态定义、模型简化、反馈、信息价值、不确定性、决策边界、跨问统一和求解结构等不同视角生成候选。
4. 第三轮组合存在因果或数学联系的异质候选，并主动寻找反例。
5. 在 `题目分析报告.md` 内记录创新沙盒。候选可以很多，采用项不设配额。

### 证据环：严格收敛

编程阶段把准备实现的候选登记到 `PROJECT_ROOT/results/创新证据清单.json`，状态依次为：

`HYPOTHESIS -> PROTOTYPED -> VERIFIED -> ADOPTED`，或转为 `DROPPED`。

- `HYPOTHESIS`：只有机制假设，不得进入正文结论。
- `PROTOTYPED`：存在最小实现，但尚未完成公平对照、证明或边界测试。
- `VERIFIED`：代码、证明或实验产物存在，量化主张可复现。
- `ADOPTED`：确认对回答题目有实质价值，允许写入正文和摘要。
- `DROPPED`：记录淘汰理由，防止后续重新包装成创新。

清单结构和门禁见 `references/创新证据协议.md`。论文手只能表达 `ADOPTED` 项，不能在写作阶段新增创新。

## 创新来源

依次扫描但不强制命中：

| 来源 | 核心问题 |
|---|---|
| 问题与目标重构 | 题目真正需要的是单点数值、策略、阈值、风险还是信息价值？ |
| 假设与状态重定义 | 哪个常规假设最影响结论，是否遗漏隐藏状态或内生参数？ |
| 模型简化 | 能否利用单调性、对称性、支配关系、充分统计量或可分性严格降维？ |
| 物理与几何简化 | 能否在保持目标判定量的前提下做对称约简、投影、包络或降阶？ |
| 模型增强 | 是否遗漏反馈、时序、空间、网络或多主体耦合？ |
| 跨问统一 | 前一问的信息能否成为后一问的状态、约束或决策价值？ |
| 算法简化 | 能否以解析预筛、剪枝、缓存、递推或分解消除不必要计算？ |
| 算法增强 | 基线求解器的具体失败机制是否需要专用改进？ |
| 数据与信息 | 哪些已有信息被浪费，样本或测量能否按决策价值主动分配？ |
| 不确定性与风险 | 参数误差怎样传播到决策翻转、后悔值或安全边界？ |
| 理论性质 | 是否可证明上下界、误差界、复杂度、凸性、单调性或不变量？ |
| 反事实与解释 | 删除模块、限制资源或改变信息条件后，结论为什么变化？ |

物理或几何候选必须读取 `references/物理几何简化.md`；求解或算法候选必须读取 `references/求解创新路由.md`。

## 创新认定

一项创新至少满足下列一种价值，并通过证据环：

- 改变状态、决策时序、约束或问题之间的关系，产生新的可解释结论。
- 在严格等价或可控误差下显著简化模型、算法或计算复杂度。
- 给出可证明的安全内界、保守外界、最优性界或决策边界。
- 在公平基线和相同信息条件下改善目标、风险、稳定性或可解释性。
- 把复杂最优解转化为可执行的分段规则、阈值或资源配置原则。

以下内容不得单独认定为创新：

- 通用算法改名、参数微调或无必要地叠加模型。
- 仅增加求解器数量、图表数量、灵敏度数量或仿真次数。
- 只做 GPU、并行或向量化但未改变可求解规模和方法结构。
- 没有真实代码、证明、结果文件或可追溯文献的宣传性表述。
- 只与故意设置的弱基线比较，或为靠近范文结果而调参。

## 三角色接口

- 建模手：维护题目分析报告中的领域机制、数学结构、机制缺口和 `HYPOTHESIS` 候选，不预写提升数值。
- 编程手：先实现基线，再做候选最小原型、公平对照、消融、证明和边界测试，维护创新证据清单并运行审计。
- 论文手：只使用 `ADOPTED` 项；按实际论证需要放在摘要、方法和结果中，不机械重复固定话术或固定展示次数。

## 完成门禁

编程阶段和论文 `W1/W2` 前运行：

```powershell
python "<SKILL_ROOT>/references/roles/innovation-special/scripts/innovation_audit.py" `
  "<PROJECT_ROOT>/results/创新证据清单.json" `
  --project-root "<PROJECT_ROOT>" --strict
```

允许清单中没有 `ADOPTED` 项；不允许 `VERIFIED/ADOPTED` 缺少实现、证明、结果或失效边界。审计通过只证明证据合同完整，不能替代独立 `P2/W1/W2` 语义验收。
