# 计算加速（GPU/并行）参考

目标：数模题计算量超限时，先做**负载结构分析**，再选加速路线；GPU 只在批量规模足够大时才有意义。
> 实证：2024 CUMCM A 题（板凳龙）全流程约 8000+ 时间步、每步 224 次串行链式求根。串行 Q3 约 6 min；
> 跨时间步 numpy 向量化后 Q3 约 16 s（约 30×）；碰撞窄相按候选对批量后 500 步 35×。

## 1. 何时需要加速（触发条件）

- 预计总时间步（或采样点）> 5000，或单段扫描 > 30 s；
- 同一计算在扫参/二分/网格中被反复调用（如最小螺距二分、终止时刻定位）；
- 用户环境 CPU 单核打满且运行时间影响交付节奏。

先估工作量：`单步耗时 × 总时间步`。若 < 60 s，不加速；否则按下方策略。

## 2. 计算资源探查（建模前/编程前）

```python
# CPU 核数
import os; os.cpu_count()
# GPU：nvidia-smi；Python 侧检测
import importlib
gpu_libs = {m: importlib.util.find_spec(m) is not None for m in ["torch", "cupy", "numba"]}
```
- 有 NVIDIA GPU（nvidia-smi 存在）且装有 torch/cupy → 可走 GPU 路线。
- 只有 CPU → 用路线 A（numpy 向量化）或 C（multiprocessing）。
- 无 GPU 库时**不静默装大依赖**：先报阻塞，或按用户许可用 CPU 路线。

## 3. 负载结构分析（先想清楚再动手）

数模计算通常分三类结构，决定并行方式：

| 结构 | 特征 | 可并行性 |
|---|---|---|
| 纯独立采样 | 各采样点无依赖 | ✅ 完全并行（采样/扫描/网格） |
| 串行链 + 时间步并行 | 步内串行（如链式递推 h_i 依赖 h_{i-1}）、步间独立 | ⚠️ 把手串行、时间步并行 |
| 全局耦合 | 各步相互依赖（如在线优化、迭代） | ❌ 难并行，考虑算法降维 |

物理/机理题常见"串行链 + 时间步并行"：**把 (T, 步内变量) 组织成数组，步内串行循环、每一步对 T 同时运算**。
示例（2024A 板凳龙）：
```python
# 链式递推：224 次串行，每次对 T 个时间步批量牛顿求根
for i in range(1, 224):
    s = sig[:, i-1] - d                      # 初值
    for _ in range(6):                        # 批量牛顿
        p = path.point(s); Tt = path.tangent(s)
        chord = hypot(p-target); g = chord - d
        s = clip(s - g*chord/denom, prev-2d, prev-0.4d)
    sig[:, i] = s
```
碰撞/距离等全对判定天然可并行：按候选对一次性向量化 SAT/距离。

## 4. 三级加速策略（按性价比）

### 路线 A（默认，纯 numpy，零依赖）——10~40×
- 把串行逐时间步循环改写为 `(T, ...)` 数组批量运算。
- 根求解用**批量牛顿**代替 `scipy.optimize.brentq`（brentq 无法向量化；牛顿+紧括区间收敛足够快）。
- 碰撞窄相把 `scipy.optimize`/逐对循环改为按候选对向量化 SAT（分离轴投影 `einsum`）。
- **验证**：批量结果与串行基线关键数值一致（位置差 <1e-9、碰撞标记逐点一致）。

### 路线 B（GPU，torch/cupy）——批规模大时 50~200×
- 前提：装有 torch/cupy 且 GPU 可用（`torch.cuda.is_available()`）。
- 把路线 A 的数组换成 GPU 张量（`np.` → `xp.`，注意 `hypot/einsum/clip` 的等价写法），
  碰撞全对判定一次 kernel 完成。
- **触发阈值**：单批 > 1e4~1e5 个采样点时 GPU 的 kernel 启动/传输开销才被摊薄；
  3000~8000 步的题用路线 A 通常已够（2024A 实测路线 A 即 30×）。
- 避免：小批规模频繁 `cpu()/cuda()` 往返；用 `torch.no_grad()`/纯推断。

### 路线 C（multiprocessing，24 核）——约核数倍
- 最省事：把扫描/采样按核数切 `Pool.map`，几乎不改核心算法。
- 代价：内存×核数；共享可变状态需小心（只读输入 + 各自返回值）。
- 适用：路线 A 不易改写（如路径分段复杂）或批规模不够大不值得上 GPU。

## 5. 何时 GPU 真正划算（决策）

| 场景 | 推荐 |
|---|---|
| 总采样点 < 5e3 | 不用加速或路线 C |
| 5e3 ~ 1e5，结构为串行链+并行时间步 | **路线 A**（numpy 向量化即可 10~40×） |
| > 1e5，或含大量全对判定（碰撞/距离矩阵） | **路线 B**（GPU）或 A+C 组合 |
| 每步间有耦合、需在线迭代 | 先降维（见 `元能力` #1/#3），别硬并行 |

## 6. 加速后验证（必做，不可省略）

- **一致性**：随机取 ≥5 个采样点，批量与串行结果逐点对比（位置/速度/碰撞标记/目标值），
  相对差 < 1e-9 或逐点一致。
- **数值收敛**：加速不应改变结论的收敛性（时间步收敛、边界翻转仍在）。
- **可复现**：加速版写入复现清单/代码库，随机种子与参数不变。

## 7. 反模式

- 为提速把 brentq 换成"更宽松"的求根导致结果漂移 → 必须用牛顿+紧括区间并复核残差。
- GPU 上跑 100 步的小批量 → kernel 开销反而更慢，先用路线 A。
- 并行改写了模型/约束/边界条件 → 违反"结果必须与串行一致"。
